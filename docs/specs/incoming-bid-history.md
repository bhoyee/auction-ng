# Incoming pre-bids and wallet-aware bid actions

**MONEY/BID CHANGE — needs human review.** This change adjusts advisory bid-button affordability checks; server reservation, ledger, acceptance, cancellation and launch rules stay authoritative and unchanged.

Bid History has an Incoming tab on mobile and web. It lists only the signed-in buyer's active/launching pre-bids for scheduled lots, with photo, friendly item ID, private maximum, actual active reservation, launch date and server-aligned countdown. A Manage/Change or cancel action opens the existing item-level pre-bid controls; it does not cancel a bid or release money merely by opening the page. Cancellation before launch uses the existing free cancellation flow. Confirmed cancelled pre-bids appear in a separate, independently paginated section of Cancelled. Launched pre-bids leave Incoming and their accepted bids appear in existing live history.

`GET /buyers/prebids?view=incoming|cancelled&limit=10&cursor=…` requires buyer authentication, rejects unknown query fields, has a maximum page size of 50, sets `Cache-Control: no-store`, and scopes cursors to buyer plus view. Responses are validated by shared Zod schemas and the typed buyer client. Related photos/locations/holds use a fixed number of queries. The additive `pre_bids_buyer_history_idx` supports owner/date/ID pagination. No new configuration variables or dependencies.

Bid now is disabled for a confirmed insufficient available balance, including disclosed fees. Top up wallet appears only for a confirmed shortfall; a successful balance refresh removes it silently. An unknown/unavailable balance disables new submissions rather than pretending it is zero (a confirmed missing wallet counts as zero). When replacing a same-item reservation, compare only the additional amount needed with available funds. Never count reservations on other lots. Leaders use their current accepted commitment; scheduled pre-bid changes use their existing active pre-bid total. All calculations use safe integer kobo in the shared fees module. The backend still checks current funds transactionally. Saved pending operations retain their exact retry path so an already-created reservation cannot disable reconciliation.
